## RKC catalogues itself without recursion

From a clean RKC checkout:

```sh
make self-catalogue
rkc query --dir dist/self-catalogue/atlas --graph-hops 2 \
  "model qualification resource guard"
rkc query --dir dist/self-catalogue/atlas --graph-hops 2 \
  "self catalogue recursion generated output"
```

The workflow stages the exact committed Git tree in a separate temporary
directory. Generated output, caches, weights, runtimes, binaries, coverage
data, and the working tree are not inputs. Publication is atomic and the
finished atlas is checked before it replaces any prior catalogue.

Measured at RKC commit `58cd6ea`:

| Nodes | 10,856 |
| Symbols | 6,155 |
| Edges | 29,707 |
| Evidence records | 45,589 |

| High-confidence secret findings | 0 |

| Deterministic digest | `d74f4795b8073eedfbfb909a833f4fb800770c9e0730c779a4b48a80e5b9550d` |

The first query ranks the model-qualification resource-policy schema first.
The second ranks `scripts/self-catalogue.sh`, `docs/SELF_CATALOGUE.md`, and the
architecture boundary first. These are evidence-linked canonical objects, not
generated prose.

RKC can also produce bounded, redacted packets ready for a qualified local LLM:

```sh
rkc synthesize \
  --dir dist/self-catalogue/atlas \
  --query "model qualification resource guard" \
  --limit 3 \
  --packet-only \
  --out dist/showcase/rkc/evidence-packets \
  --force
```

This generated three packets with no model process, no repository execution,
and no published model claim.

The same committed atlas is the browser demonstration:

```sh
rkc_ready_directory=$(mktemp -d)
chmod 700 "$rkc_ready_directory"
scripts/with-rkc-limits.sh ./bin/rkc serve \
  --dir dist/self-catalogue/atlas \
  --addr 127.0.0.1:0 \
  --workbench \
  --workspace . \
  --ready-file "$rkc_ready_directory/ready.json"
```

The served GUI fetches bounded overview, facet, search, entity, evidence, and
graph API responses rather than loading the complete 29,707-edge graph at
startup. Its command centre exposes 19 bounded CLI workflows without a shell;
it accepts requests only on an authenticated loopback origin, runs one
bounded job at a time under the same resource guard, and retains a read-only
static fallback. Direct workbench serving cannot use `--open`; a trusted
launcher consumes the owner-private readiness receipt without logging its
one-time `browser_url` capability. For an automatic browser launch, use
`rkc open --workbench .` and let the outer process perform that exchange.
That preferred route also supplies continuous outer-process pre-emption for
configured higher-priority workloads during atlas loading; direct serving
rechecks before and after preparation and continuously once the server starts.

## A new, high-traction external repository

The external example is
[`img2threejs/img2threejs`](https://github.com/img2threejs/img2threejs), created
on 2026-07-15. At the 2026-07-27 selection snapshot it had 5,620 stars and 435
forks, used Python, and declared Apache-2.0. RKC pins commit
[`f1ade81d45252ede20323d74a5b269c819f75245`](https://github.com/img2threejs/img2threejs/commit/f1ade81d45252ede20323d74a5b269c819f75245)
and tree `455c305b1f13e58e15f60811c609a2e46e54e6d6`; moving `main` is never an
analysis input.

```sh
rkc scan \
  --no-python \
  --ref f1ade81d45252ede20323d74a5b269c819f75245 \
  --clone-depth 1 \
  --out dist/showcase/img2threejs/atlas \
  --state-dir dist/showcase/img2threejs/state \
  --cache-dir dist/showcase/img2threejs/cache \
  https://github.com/img2threejs/img2threejs.git

rkc check \
  --coverage dist/showcase/img2threejs/atlas/coverage.json \

  --export-manifest dist/showcase/img2threejs/atlas/rkc-export-manifest.json \
```

```sh
rkc synthesize \
```

mode and answered with citation validation. Until then, RKC deliberately
provides lexical search, GraphRAG traversal, browsing, MCP access, and
model-ready packets without pretending an unqualified model is safe to use.

## Compiler-grade self-analysis with SCIP (2026-08-31)

RKC's own source compiles cleanly with compiler-grade Go semantics. The
workflow pins a host-built `scip-go` indexer to its exact SHA-256, generates a
repository-contained index, strictly validates it with the same parser used by
imports, and lets the scan import it through the normal digest-bound path:

```sh
make build
./bin/rkc scip pin --language go --tool "$(command -v scip-go)" --version v0.2.7
./bin/rkc scan \
  --no-python \
  --scip-generate go \
  --exclude .rkc-smoke --exclude .rkc-coverage \
  --out /tmp/rkc-scip-atlas --state-dir /tmp/rkc-scip-state --force .
```

Measured at RKC commit `20890e7` (working tree, `--scip-generate go`):

| Measure | Without SCIP | With compiler-grade SCIP |
|---|---:|---:|
| Relationship resolution | 31.35% | **84.89%** |
| Resolved edges | 10,100 / 32,218 | 126,418 / 148,917 |
| Semantic-parsed artifacts | 0 | 246 Go files |
| Compiler-resolved evidence | 0 | 254,535 records |
| External dependency docs skipped | n/a | 42 (`SCIP-EXT` diagnostics) |

Importing the pinned compiler index therefore resolves **12.5x more
relationships** and marks every Go package compiler-parsed, while external
standard-library documents are skipped with explicit bounded diagnostics
rather than becoming repository truth. `rkc scip verify`, `rkc scip
languages`, and `rkc scip generate --tool-args ...` cover inspection and
project-specific indexer flags; the workbench command center exposes the same
workflows.
